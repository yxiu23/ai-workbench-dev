### 2.2 一个"本以为可行"的方案被官方文档否掉

我原本准备了**提交 + 轮询**的异步方案（CF 官方给 524 的建议原文就是 *"Implement status polling of large HTTP processes"*）。
但 `ctx.waitUntil` 的文档写明：

> *"For HTTP-triggered Workers, `ctx.waitUntil()` can extend execution for up to **30 seconds** after the response is sent or the client disconnects. **This is not a limit on the total wall time of an HTTP request**."*

⇒ **后台最多跑 30 秒，远不够出图** ⇒ 这条路不通。
同时另一句给了方向：

> *"If the client is still receiving the response, **including a streamed response body**, the Worker invocation remains active without `ctx.waitUntil()`."*

⇒ **流式保活是唯一的路**（Worker 可以一直活着，只要客户端还在收）。

### 2.3 所以这次加固了什么（Worker R9ZX）

既然 R9ZI 的"等 50 秒再发首字节"没走通，就把它推到极限：

| 项 | R9ZI | R9ZX | 为什么 |
|---|---|---|---|
| 首字节延迟（GRACE） | 50 秒 | **1.2 秒** | 兜住任何"必须在 X 秒内看到响应"的假设（X ≥ 1.2s） |
| 心跳间隔（BEAT） | 15 秒 | **5 秒** | 兜住"两次读之间不能超过 N 秒"的那类语义 |
| 响应 Content-Type | `text/plain` | **`text/event-stream`** | CF 对 SSE 有明确的"流式直通、不缓冲"处理；普通 chunked 有被边缘缓冲的可能（缓冲 = 首字节一直不出去 = 524） |
| 心跳内容 | `\n` | `:\n\n`（合法 SSE 注释） | 同上。**对前端零影响**：解包是按最后一个魔数切的 |
| 额外头 | — | `X-Accel-Buffering: no` | nginx 系的"别缓冲"惯例头 |

# 【附录 A】2026-10-10 傍晚 · 524 真根因**查明并推翻前两次判断** + 三件新修复

## A.1 ★★★ 524 的真根因：**不是 CF↔Worker，是 Worker 的 subrequest**

修贴了 R9ZX 之后仍然 524 ⇒ 我跑了那条决定性的 `/ktest`（**零成本**，我有 token，不用等修）：

| 测试 | 首字节 | 结果 |
|---|---|---|
| **A 带 `X-Aiwork-Slow-Ok: 1`** | **1.5 秒** | `200` + `X-Aiwork-Keepalive: 1` ⇒ **保活生效 ✓** |
| **B 对照组（`force=1`，不保活）** | **140.6 秒** | **`200`** ← ⚠ **不是 524！** |

**对照组等了 140 秒却拿到 200** ⇒ **CF 对 Worker 根本没有 125 秒限制**。

⇒ **真正的 125 秒墙在 Worker 内部那一跳**：
`fetch("https://api.apiyi.com/…")` 是 **CF 发出的 subrequest**，对 CF 而言 `api.apiyi.com` 是
**外部源站** ⇒ **照样吃 125 秒 Proxy Read Timeout** ⇒ 到点 CF 给这个 fetch 塞一个 **524 响应**
（**不是网络异常**）⇒ Worker 不知情、`return new Response(resp.body, {status: resp.status})`
**原样透传** ⇒ 用户看到 524。

**⇒ 我前两轮修的"保活"修错了地方**：保活只让 **Worker 能活 360 秒**，
但 Worker 手里那个上游请求**只能活 125 秒**。**这是 CF 平台层的硬限制，前端和 Worker 代码都改不了。**

**⇒ 唯一出路：让上游请求在 125 秒内返回。** 三条：
1. **换节点试**（零成本，见 A.2）
2. **换快的模型/档位**（SeeDream Flash / FLUX / 低清晰度）
3. **慢档改走速创异步通道**（速创是"提交秒回 + 4 秒轮询"，结构上不撞）

## A.4 关于「我开代理的，和这个有关系吗」——**没关系**

524 是 **Cloudflare 服务端判定并返回**的状态码；代理在**你和我之间**，改变不了 CF 对

## A.5 关于「扣过费了」

APIYI 官方口径就是"客户端断开不取消上游任务"。这条**没法避免**，只能靠"不再发会超时的请求"来绕。

- **不准**：目前角度调整给上游的只有**一句文字描述**（如「更俯视约 15°、向右环绕约 20°」），
  **没有把角度信息变成视觉参考**。纯文字对这种 3D 几何约束**本来就弱**。
  内嵌角度参考图（比如一张同姿态的示意图 / 3D 线框）**理论上会明显更准**，但属于**新功能**，要单独评估。
- **分辨率变大**：**正常，且是设计**。上游只接受**离散档位**（如 `1024*1024` / `2048*2048`），
  所以 `wyPixels`/`apiyiSize` 会把"比例+清晰度"合成档位像素串 ⇒ 原图 800×600 会被"标准化"到 1024×1024。
  **要原尺寸输出，得走能接受任意尺寸的模型**（多数不行）。
