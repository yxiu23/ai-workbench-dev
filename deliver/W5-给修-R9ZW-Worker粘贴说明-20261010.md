## 一、这一版相对**你线上现在那版（R9ZI）**只多了什么

**只加了一条自检路由**，其余逐字节不动：

- **`/ktest?ms=<毫秒>[&force=1]`** —— **不出网、零费用**的保活自检。
  它**直接复用保活函数本体**（不是抄一份逻辑），所以它测的就是真链路。
- `/health` 的 `caps` 里多一个 **`keepaliveSelfTest: true`**
- 版本号 → `R9ZW-20261010`

**为什么非加这一条**：你说「我觉得可能不是 APIYI 服务方的问题」—— 对，**是 CF 的 125 秒墙**。
我已经排除了两个怀疑（线上 Worker 已是 R9ZI、线上前端确实带了 `X-Aiwork-Slow-Ok`），
但「保活到底有没有绕过那堵墙」**没办法零成本验证**：
真调一次慢模型要花钱、还不保证慢过 50 秒；用"永不完成的请求体"做探针也不行
（实测：CF 会先等客户端 body 传完才回，A/B 两条各等 180 秒都没响应 ⇒ 测量无效）。
⇒ 加这条路由，把这件事从"猜"变成**一条 curl 就能复验的事实**。

## 三、贴完怎么验（两条命令，都零成本）

**① 版本到位（3 秒）**

```bash
curl -s -i -X OPTIONS https://media.gaze23.work/ | grep -i x-aiwork-proxy
# 期望：x-aiwork-proxy: R9ZW-20261010
```

或直接开 `https://media.gaze23.work/health`，`version` 应为 `R9ZW-20261010`，
`caps` 里应有 `"keepaliveSelfTest": true` 与 `"slowKeepalive": true`。

**② 保活到底生效没有（决定性，约 2.5 分钟）**

```bash
curl -N "https://media.gaze23.work/ktest?ms=140000&token=k7m3x9b2n5p8q1w4e6r9t3y6u8i2o5a7"
```

| 现象 | 含义 |
|---|---|
| **约 50 秒**开始吐字节，最后出一段 `{"ok":true,"keepalive":true,…version":"R9ZW-20261010"}` | ✅ **保活生效** ⇒ CF 的 125 秒墙已经被绕过，角度调整不该再 524（若还 524，那说明你测的是贴之前的旧报错） |
| **约 125 秒**回 `524` | ❌ **保活没生效** ⇒ 告诉我，我换方案（改"提交 + 轮询"架构） |

对照组（**确信**应该 125 秒 524，用来证明上面那条不是错觉）：

```bash
curl -N "https://media.gaze23.work/ktest?ms=140000&force=1&token=k7m3x9b2n5p8q1w4e6r9t3y6u8i2o5a7"
```

## 四、这一版**没有**动的地方（回退安心区）

- 基线 IMPL-150 一行未换，老批次补丁逐字保留
- `/media/apiyi/*` 白名单、`/media/seg/*`、`/media/img`、`/upload`、`/task`、`/llm/*`、`/userdata` **全部原样**
- **保活仍只在三个条件同时成立时启用**：① APIYI 通道 ② POST ③ 请求头带 `x-aiwork-slow-ok: 1`
  ⇒ 其余一切请求（含所有 GET、轮询、速创/硅基/百炼三条通道）走原来的代码路径，**逐字节不变**
- `/ktest` 走 `requireAuthReq`（与 `/media/*` 同口径）—— **不开匿名长连接口子**；`ms` 上限 300000

## 五、可选旋钮（不配就用默认，不配也行）

| 变量名 | 默认 | 含义 |
|---|---|---|
| `R9ZI_GRACE_MS` | `50000` | 先等上游多少毫秒；这段时间内返回就原样透传 |
| `R9ZI_BEAT_MS` | `15000` | 切保活后每多少毫秒写一个换行续命 |

⚠ 两个值**都必须小于 125000**（CF 的 125 秒首字节上限），否则等于没修。
