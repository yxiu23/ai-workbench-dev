## 一、先说结论：之前查的方向错了

你骂得对。前四轮（R9ZI / R9ZW / R9ZQ / R9ZX）我都在做**「慢请求保活」** ——
想办法让 CF 那道墙"绕过去"。10-10 的实测把这个方向**彻底否掉了**：

- `/ktest?ms=140000`（纯等待、零上游请求）曾撑到 **180s**
- `/ktest?ms=150000` 却在 **170s 一个字节都没收到**

⇒ **CF 的 125 秒墙是"概率性触发"**，保活只能把成功率往上抬一点，**永远不保证**。
Worker 里 189 行注释其实早写着"贴了保活后仍然 524"——我自己没当回事。

**正解不是"让请求扛过 125 秒"，而是"让请求根本不用等"：**

```
旧链路（同步）：前端 ──发请求──→ Worker ──等 200~400 秒──→ APIYI
                                    ↑ 卡在这里，CF 125 秒就断（524）

新链路（异步）：前端 ──提交──→ Worker ──秒回"收到"──→ 前端（2 秒内返回）
                            Worker 把活记进 KV
                 Cron（每分钟，平台自己触发，不吃用户请求的 125 秒）──→ APIYI
                 前端 ──轮询──→ 取回结果
```

**用户侧永远只碰两次短请求**（提交 / 轮询），每次都在 125 秒内 ⇒ **墙无从触发**。

**其中三条是本批的"命门"，单独说**：

1. **提交不等上游**（量化）：上游要 400ms，提交在 **100ms 内返回**；Cron 侧确实等满了 400ms。
2. **防双重计费**：拿到 taskId 之后失败 ⇒ **禁止**退回同步重试（否则上游已受理、再发一次就是双倍扣费）。
