## 一、为什么要贴（一句话）

上一轮我用 `/ktest` 证明了「Cloudflare 对 **Worker 本身**没有 125 秒限制」。
但用户看到的 524 是 **Worker 内部去请求 api.apiyi.com 那一跳**（subrequest）被 CF 掐断的。
**那一跳到底吃不吃 125 秒的墙，只有真发一次才知道。**
R9ZQ 就是给我这个"真发一次"的口子 —— 它**零成本、零计费**（只 GET 一个纯延迟地址，不带任何密钥）。

**贴完我就能一句话定论：524 是 CF 平台硬限制（改代码没用，必须换上游），还是我们这边能绕。**
不贴的话，这个结论永远只能靠推测。

## 二、怎么贴（Cloudflare 控制台 · 中文界面）

1. 打开 **Cloudflare 控制台** → 左侧 **「计算（Workers）」** → **「Workers 和 Pages」**
2. 点进 Worker **`ai-media-proxy`**
3. 右上角 **「编辑代码」**（Quick Edit）
4. **全选** 编辑器里的旧代码（`Ctrl+A`）→ **删除**
5. 打开 `R9ZQ-Worker-完整代码.js`，**全选复制** → 粘贴进编辑器
6. 右上角 **「部署」** → 确认

> ⚠ 环境变量**不用动**（`AUTH_TOKEN` / `APIYI_API_KEY` / `SPEEDX_KEY` / `IMAGESEG_AK` / `IMAGESEG_SK` 都还在）。

## 四、贴完把这条命令的结果发我（关键）

终端里跑（`<TOKEN>` 换成你的 `AUTH_TOKEN`）：

```
curl -N "https://media.gaze23.work/ktest?probe=https%3A%2F%2Fhttpbin.org%2Fdelay%2F200&token=<TOKEN>" -H "x-aiwork-slow-ok: 1"
```

**它会等最多 200 秒**（不是在卡，是在真的量时间）。看最后吐出来的 JSON：

| 你看到的 | 含义 | 下一步 |
|---|---|---|
| `waitedMs` **> 130000** 且 `probeStatus` = **200** | **subrequest 不受 125 秒限制** ⇒ 524 另有其因（我们要继续查别处） | 告诉我，我继续挖 |
| `waitedMs` ≈ **125000** 且 `probeStatus` = **524** 或 **504** | **subrequest 确实吃 CF 的 125 秒墙** ⇒ 代码救不了 | 只能换上游（见下） |
| 命令直接 `524` 没吐 JSON | 连保活流都被断 ⇒ 更严重的墙 | 告诉我 |

## 五、如果结论是"墙存在"（代码救不了）

那么**唯一出路是让上游请求在 125 秒内返回**。现成的、不用再贴代码的方向：

1. **换 APIYI 节点**（在 Worker 的「设置 → 变量」里加一个普通变量）：
   - 变量名：`APIYI_BASE`
   - 值：`https://api-cf.apiyi.com`
   - 原理：`api.apiyi.com` 是 openresty 源站（不走 CF），而 `api-cf.apiyi.com` 本身就走 CF ⇒
     CF→CF 那一跳**可能**走内部路由、不吃 125 秒（未验证，值得一试）。
   - ⚠ 改完**不用重贴代码**，保存变量即可生效。

2. **慢档一律走速创（S 档）**：速创是「提交 → 拿任务 id → 轮询」两态结构，
   每一跳都是独立短请求，**结构上就不会撞 125 秒**。角度调整已经默认走速创档。

3. 如果你要用代理跑，注意：**代理与 524 无关**（524 是 CF 服务端判定）。
   代理不通会表现为 `Failed to fetch`，不会变成 524。
